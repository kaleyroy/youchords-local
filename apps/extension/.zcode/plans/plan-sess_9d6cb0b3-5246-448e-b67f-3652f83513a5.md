# Bridge 标记 + 词时间轴修复(第二轮)

## Context

上轮修复后用户反馈两个问题(视频 1GWQ-oFYn4M,Gemini 转写源,Auto/Always 模式):

1. **依然没有 Bridge 标记**。根因补查实锤:
   - YouTube 路径:存库的 `originalSentences` 是 `createSentenceSRT()` 从**清洗后词流**生成的(`youtubeSubtitles.js:1096-1100`,括号已被 `cleanWordText` 滤掉);`fetchWordsFromYouTube` 返回的**原始句(含 `[Bridge]`,`youtubeSubtitles.js:926-948/952-959`)在 1939 行解构时被丢弃**。且 resolver(`databaseManager.js:792-797`)还优先用清洗版 SRT 重解析覆盖。→ Pass 2 恢复源永远没有标记。
   - Gemini 路径(用户当前源):提示词(`geminiTranscription.js:317/417`)**从未要求输出段落标记**,Gemini 自然不会给 `[Bridge]`。
2. **Bridge 段"oh 一闪而过、后续歌词提前滚动"**。词时间链路:`wordSRT` 恒为 null(`youtubeSubtitles.js:2053`,面板刻意句级化,`databaseManager.js:895` 归一化也强制清空),所以 `parseSRT` 对**每个句子内的词做均匀分布估算**(`lyricsAndChordsButton.js:5595-5601`)。Gemini 把 "Ooooh" 与后续句合并成长句时,后续词的估算起点大幅提前——正是症状。

用户已确认:接受重抓字幕;启用 Bridge 启发式兜底;要"长音填格"视觉。

## 修改

### 1. `utils/geminiTranscription.js` — 转写契约升级(核心)

- **默认提示词**(两处硬编码,317 与 417 行,抽成常量复用)追加两条要求:
  a. 段落变化时(intro/verse/pre-chorus/chorus/bridge/instrumental/outro)先输出一行**独立方括号标记行**(如 `[Verse 1]`、`[Bridge]`,1-2 秒短行,时间对准段落起点);
  b. 每行字幕附 `words` 数组,逐词 `{text, start, end}`(SRT 时间戳格式),覆盖该词真实发声区间;**拖长音(如 held "oh")的 end 要延伸到持续结束**。
- 两个十进制秒 fallback 提示词(399/407 行)做同样追加(措辞用 decimal seconds)。
- **默认 schema**(706-754 行):subtitles items 增加可选属性 `words: array of {text, start, end}`(SRT 格式描述),**不加入 required**(模型可省略,兼容旧响应);示例同步更新。
- 响应解析:subtitles 透传 `words`(SRT 时间串→秒,复用现有 SRT 时间解析)。

### 2. `utils/youtubeSubtitles.js` — 保存原始句与词时间

- 1939 行解构改为同时保留 `originalSentences`(fetchWordsFromYouTube 的原始版,含括号标记)。
- YouTube 保存 payload(2070-2083)新增:`rawOriginalSentences`(原始句)、`youtubeWordTimings`(json3 词 `[{text,start,end}]`,精确起点,丢弃前留档)。
- `convertGeminiToInternalFormat`(1260-1322):sub.words 存在时用**真实词时间**填充 `originalSentences[].words`(替换现在的均分估算),并返回 `wordTimings` 平铺数组;两个 Gemini 保存点(1718-1728、1994-2006)新增存 `geminiWordTimings`。

### 3. `utils/databaseManager.js` — schema 门禁

- subtitles 记录 allowlist(607-634)新增三个字段:`rawOriginalSentences`、`youtubeWordTimings`、`geminiWordTimings`(记忆中的坑:不加 allowlist 会被静默丢弃)。

### 4. `buttons/lyricsAndChordsButton.js` — combine 层接线

- `combineLyricsAndChords` 在 `normalizeActiveSubtitlesData`(≈7247)**之前**捕获原始记录 `rawRecord`。
- **词时间重映射**:新增 helper `remapWordsToTimings(lines, timings)`(仿 parseSRT 匹配循环 5554-5601:顺序游标、去标点小写文本匹配、行时间窗容差),在 tagSectionMarkers 之后调用;timings 按 `activeDefaultSource` 选择(gemini→`rawRecord.geminiWordTimings`,youtube→`rawRecord.youtubeWordTimings`),`useTranslation` 时跳过;**匹配率 <50% 整体放弃**(防脏数据)。
- **tagSectionMarkers 扩参**:标记恢复源在现有 `useOriginalSentences` 基础上增加 `rawRecord.rawOriginalSentences`(youtube 活跃时)/`rawRecord.geminiOriginalSentences`(gemini 活跃时),已有 ±1.5s/±2.5s 去重自然兜住重复。
- **默认视图守卫**:渲染循环(~4822)跳过 `line.isSectionMarker` 行(新提示词产出的 `[Bridge]` 行不再以小写 `[bridge]` 歌词形式出现在默认视图,保持默认视图与现状一致)。

### 5. `buttons/measureChartView.js` — Bridge 启发式 + 长音填格

- **Bridge 兜底**:`deriveSectionsFromMetadata` 输出后做后处理——名为 `Verse N` 且全曲恰好出现一次、且其前后(按时间)均存在 `Chorus` 段的条目改名为 `Bridge`(仅无真实标记的兜底路径生效)。
- **长音填格**:新增 `applyHeldWords()`,在 `buildMeasures()` 末尾调用(两种模式共用):按 wi→小节映射取相邻词对,若下一词与本词相隔 ≥2 小节,则在本词后至下一词前的空小节填入 `{word, held: true}`(每词最多 3 格;启用了段落头时,遇段落边界即停,不跨段填充)。渲染:`<span class="yc-m-word yc-m-word-held">` 无 data 属性(不参与点击/高亮),CSS 淡化(opacity≈0.45、无 hover)。
